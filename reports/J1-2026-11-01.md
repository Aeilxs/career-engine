## Persistence / restart / fault injection

- Real process kill: `tests/test_restart_process.py` (default suite) imports, creates an application and a transition over HTTP, sends SIGKILL to the server process, restarts and verifies offer, bytes, hash, history and XLSX.
- Injected SQL failures (real SQLite triggers, no mocks): import (rolls back offer/revision/snapshot; an unreferenced object file is reported as an orphan, never as data), application creation (new dossier folder removed), and stage transition with the failure placed on either the event insert or the stage update (neither a partial transition nor an orphan history event remains).
- Concurrency: 8 concurrent identical imports → 1 offer / 1 revision; 6 concurrent creations → 1 application and 1 dossier; 8 competing job claims → exactly one winner; an expired lease is reclaimed and the old worker's completion is rejected by generation fencing.

## Open limitations / NOT TESTED

- **No React/Vite/TypeScript.** The ticket calls for it but AGENTS.md makes it a separate maintainer-reviewed prerequisite. The J1 UI is vanilla JS/CSS served by FastAPI. **No XLSX library**: the workbook is written with a small stdlib writer (`infrastructure/xlsx.py`); the maintainer may prefer `openpyxl`/`XlsxWriter` after review.
- The ticket lists "P0/J0 accepted" as a prerequisite; `STATUS.md` still shows P0 as pending. J1 was implemented anyway at the user's request.
- XLSX was verified with an independent stdlib reader and `openpyxl`; it was **not** opened in Excel, Numbers or LibreOffice.
- Browser E2E ran only in headless Brave/Chromium 154; Firefox and Safari were not tested. The E2E is opt-in, resolves Playwright/openpyxl ephemerally via `uv run --with` (not in `pyproject.toml`/`uv.lock`) and is **not** wired into CI (CI files are maintainer-owned). Playwright's string-eval is blocked by the app's CSP, so the script uses locator-based waits.
- `scripts/verify-j0.sh` was **not** run: it operates on the operator's `./data` and the running `career-engine` Compose project. Equivalent J0 marker persistence was exercised inside the isolated E2E project instead. The pre-existing J0 container was left untouched and still runs the old image; on its next rebuild the real `./data/career.db` will be migrated v1 → v2 (migration tested on a synthetic legacy database, **not** on the real file).
- `test_persistence.py` was edited: `user_version == 1` became `== SCHEMA_VERSION` because the approved-in-scope J1 migration raises the schema to 2. A dedicated upgrade test (v1 database with marker → v2, marker preserved) was added.
- T01 failed-remote-retrieval part and URL import are J2. T02 is checked against fixture-level annotations only (salary is kept as the source text; currency/period parsing is J3). T21: HTML/script/formula inertness, static-asset traversal, CSRF header and CSP are tested; private-URL/redirect blocking is not applicable (nothing is fetched at J1; apply URLs are only scheme/credential-validated and never requested); no secret-sentinel test was written.
- Durable job queue (REQ-018/T16) is implemented and tested, but no job kind is registered and `career worker` is an empty-registry loop; nothing in J1 enqueues jobs.
- One application per offer (`UNIQUE(offer_id)`); only `DRAFT`, `PREPARING`, `BLOCKED` are settable (APPROVED/SUBMITTING/SUBMITTED require J4–J6 gates and are refused). `recruiter_status` is unknown/read-only (REQ-027 is J7+). XLSX `approved_at`, `confirmed_submitted_at`, `last_error` and `next_action` are intentionally empty.
- Duplicate suggestions are recorded but there is no accept/dismiss UI yet. Orphan object files are reported by `career verify` but never deleted automatically (deleting could race an in-flight import).
- Snapshots are deduplicated by content hash: identical bytes imported under two different identities share one snapshot row (the first `source_ref` wins).
- Location splitting is by `;` only; "Marseille and Aix-en-Provence, France" stays one location.
- No Host-header validation (DNS rebinding); state-changing requests are protected by a required `X-Requested-With` header only. Loopback-only binding is unchanged.
- No submission, ATS, LLM, Playwright-driven ATS or live network access exists in the product code.
